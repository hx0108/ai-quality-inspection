# AI效果评估看板升级方案：从"监控"到"归因+自动改进建议"

> 目标：让看板从"告诉你指标是多少"升级为"告诉你问题在哪、为什么、怎么改"，并形成"诊断→建议→采纳→回测"的闭环，驱动AI评分系统持续自我进化。

---

## 一、背景与目标

### 1.1 现状
当前"效果评估"看板（`AiMetrics.vue` + `api/ai_metrics.py`）是**纯监控型**：
- 能显示一致性率、降级率、偏差等指标
- 能定位到"设施维护偏差大"这一层
- **不能**解释为什么偏差大，也不能给出改进建议

### 1.2 升级目标
| 能力 | 现状 | 升级后 |
|------|------|--------|
| 发现问题 | ✅ 指标监控 | ✅ 异常自动检测 |
| 定位问题 | ⚠️ 到模块级 | ✅ 到检查项级 + 偏差模式 |
| 解释原因 | ❌ 无 | ✅ 根因归因（统计+LLM） |
| 改进建议 | ❌ 无 | ✅ 可执行建议（含落地动作） |
| 闭环优化 | ❌ 无 | ✅ 采纳→生效→效果回测 |

### 1.3 设计原则（遵循 CLAUDE.md）
- **模型是裁判不是操作员**：确定性代码做检测/聚类/触发，LLM只做语义解释和建议生成
- **人在环**：所有"修改评分规则/prompt"的建议必须人工采纳后才生效
- **最小侵入**：复用现有数据（scoring_results/edit_reason/edge_case），不重构评分流程
- **渐进落地**：P1纯确定性（零风险）→ P2接LLM → P3闭环

## 二、整体架构

```
┌─────────────────────────────────────────────────────────────┐
│                    诊断引擎 (Diagnosis Engine)               │
│                                                              │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐ │
│  │ ① 异常   │→ │ ② 根因   │→ │ ③ 建议   │→ │ ④ 闭环   │ │
│  │   检测   │   │   归因   │   │   生成   │   │   落地   │ │
│  │(确定性)  │   │(统计+LLM)│   │  (LLM)   │   │(人工+自动)│ │
│  └──────────┘   └──────────┘   └──────────┘   └──────────┘ │
│       ↑              ↑              ↑              ↓        │
│   指标数据      scoring_results   DeepSeek     scoring_rules │
│                /edge_cases       /模板         /prompts      │
└─────────────────────────────────────────────────────────────┘
                             ↓
                    ┌────────────────┐
                    │  看板：智能诊断 │
                    │   建议卡片     │
                    └────────────────┘
                             ↓
                    人工 采纳/驳回 → 回测效果
```

**三层职责**：
1. **检测层（确定性）**：用阈值/规则判断"哪里异常"
2. **归因层（统计+LLM）**：聚合数据找模式，LLM解释语义根因
3. **建议层（LLM+模板）**：生成可执行建议，action_type用确定性分类

## 四、归因引擎设计

### 4.1 异常检测（确定性，P1）

定义一组**诊断规则**，每条规则 = (检测条件, 问题描述模板)：

```python
DIAGNOSIS_RULES = [
    {
        "id": "MODULE_CONSISTENCY_LOW",
        "detect": lambda m: m.consistency_rate < 95,
        "severity": lambda m: "高" if m.consistency_rate < 85 else "中",
        "problem_tpl": "{module}模块一致性率仅{rate}%，低于95%基准",
    },
    {
        "id": "MODULE_DEVIATION_HIGH",
        "detect": lambda m: m.deviation > 3.0,
        "severity": lambda m: "高" if m.deviation > 5 else "中",
        "problem_tpl": "{module}模块编辑率偏差{dev}，人工修改频繁",
    },
    {
        "id": "MODULE_FALLBACK_HIGH",
        "detect": lambda m: m.fallback_rate > 10,
        "problem_tpl": "{module}模块降级率{rate}%，AI评分不稳定",
    },
    {
        "id": "LOW_CONFIDENCE_CLUSTER",
        "detect": lambda m: m.low_confidence_ratio > 0.3,
        "problem_tpl": "{module}模块低置信度评分占比{ratio}%，AI常拿不准",
    },
    {
        "id": "OVERCONFIDENT_BIAS",   # 高置信度却被改 = 盲目自信
        "detect": lambda m: m.avg_confidence > 0.85 and m.edit_rate > 0.2,
        "severity": "高",
        "problem_tpl": "{module}模块AI过度自信（置信{conf}但修改率{edit}%）",
    },
    {
        "id": "EDGE_CASE_LOW_HIT",
        "detect": lambda ec: ec.hit_rate < 50,
        "problem_tpl": "边缘案例'{case}'命中率仅{rate}%，AI频繁漏判",
    },
]
```

每日定时（或看板打开时）对每个模块跑这些规则，命中的进入归因队列。

### 4.2 根因归因（统计聚类 + LLM）

#### Step 1：统计聚类（确定性，P1）

对每个异常模块，聚合其被修改的评分项，找出**热点检查项和偏差模式**：

```sql
-- 归因查询：设施维护模块的修改热点
SELECT 
    item_id, item_name,
    COUNT(*) as edit_count,
    ROUND(AVG(original_score - score), 2) as bias_direction,  -- 正=AI高估，负=AI低估
    ROUND(AVG(confidence_score), 2) as avg_confidence,
    edit_reason,
    COUNT(*) as reason_count
FROM scoring_results
WHERE module_name = :module AND is_edited = 1
  AND scored_at >= :since
GROUP BY item_id, item_name, edit_reason
ORDER BY edit_count DESC
LIMIT 10;
```

**偏差模式识别**（确定性分类）：

| bias_direction | avg_confidence | 模式 | 含义 |
|----------------|----------------|------|------|
| > 0.5 | > 0.8 | **漏检型** | AI自信地判合格，实际有问题（最危险） |
| < -0.5 | > 0.8 | **过严型** | AI自信地扣分，实际合格 |
| 任意 | < 0.6 | **不确定型** | AI自己拿不准（可接受，调阈值即可） |

#### Step 2：LLM根因解释（P2）

把聚类结果喂给 DeepSeek，生成自然语言根因：

```
Prompt 模板：
你是品质检查AI系统的诊断专家。以下是"{module}"模块的诊断数据：

异常：{problem}
修改热点检查项：
  - {item_name}：修改{edit_count}次，AI平均给{orig}分→人工改{final}分，
    AI判断理由："{scoring_basis_sample}"，人工修改原因："{edit_reason}"
偏差模式：{pattern}

请用一句话分析根因：AI的评分规则/prompt在哪方面缺失或偏差？
只输出根因，不要建议（建议单独生成）。
```

**示例输出**（设施维护·屋面防水）：
> "AI评分依据仅检查'有无明显渗漏'，未覆盖'细微裂缝/防水层老化'等隐蔽缺陷，属评分规则盲区。"

### 4.3 归因结果数据结构

```python
@dataclass
class Attribution:
    module: str                          # 设施维护
    rule_id: str                         # MODULE_DEVIATION_HIGH
    problem: str                         # 问题描述
    severity: str                        # 高/中/低
    pattern: str                         # 漏检型/过严型/不确定型
    hotspots: list                       # 热点检查项 [{item_id, item_name, edit_count, bias_direction}]
    root_cause: str                      # LLM根因（P2）
    evidence: dict                       # 证据：scoring_id列表、统计数字
    detected_at: datetime
```

## 五、建议生成设计（P2）

### 5.1 建议类型（确定性分类）

| action_type | 触发模式 | 落地方式 | 风险 |
|-------------|---------|---------|------|
| `add_rule` | 漏检型 + 某检查项编辑率>30% | 写入 `scoring_rules` 表 | 中 |
| `adjust_threshold` | 不确定型 + 低置信度占比>40% | 更新 `config` 阈值 | 低 |
| `refine_prompt` | 过严型 或 盲目自信型 | 写入 `prompt_templates`（待审） | 高 |
| `add_edge_case` | 边缘案例命中率<50% | 写入 `edge_case_library` | 低 |
| `human_review` | 任意高严重度 | 标记需人工复核 | 无 |

### 5.2 建议生成流程

```
归因结果(Attribution) 
    ↓
按 pattern + severity 选 action_type（确定性）
    ↓
组装 LLM 输入（归因 + 热点 + 历史规则）
    ↓
DeepSeek 生成具体建议（自然语言 + 结构化参数）
    ↓
模板校验 + action_type 修正（确定性兜底）
    ↓
Suggestion 对象
```

**LLM 建议生成 Prompt**：
```
基于以下诊断，给出1条最优先的改进建议：

模块：{module}
根因：{root_cause}
热点：{hotspots}
当前评分规则：{existing_rules_sample}

要求输出JSON：
{
  "action_type": "add_rule|adjust_threshold|refine_prompt|add_edge_case",
  "suggestion": "具体建议内容",
  "action_params": { /* 落地参数，如新增规则的扣分逻辑 */ },
  "expected_impact": "预计提升XX%",
  "priority_reason": "为什么这是最优先的"
}
```

### 5.3 建议数据结构

```python
@dataclass
class Suggestion:
    id: str
    attribution_id: str
    action_type: str                     # add_rule / adjust_threshold / ...
    suggestion: str                      # "补充屋面防水裂缝案例到评分规则"
    action_params: dict                  # {"rule_content": "...", "module": "设施维护"}
    expected_impact: str                 # "预计提升一致性率15%"
    status: str                          # pending / approved / rejected / applied
    created_at: datetime
    applied_at: datetime | None
    review_feedback: str | None          # 驳回理由（用于优化LLM）
```

## 六、数据模型（新增表）

### 6.1 诊断结果表

```sql
CREATE TABLE diagnosis_results (
    id INTEGER PRIMARY KEY,
    diagnosis_id VARCHAR(50) UNIQUE,        -- DIAG-YYYYMMDD-xxxxxxxx
    module_name VARCHAR(50),                 -- 异常模块（NULL=全局）
    rule_id VARCHAR(50),                     -- 触发的规则ID
    problem TEXT,                            -- 问题描述
    severity VARCHAR(10),                    -- 高/中/低
    pattern VARCHAR(20),                     -- 偏差模式
    root_cause TEXT,                         -- LLM根因
    evidence_json TEXT,                      -- 证据（热点、统计、scoring_id）
    status VARCHAR(20) DEFAULT 'active',     -- active/resolved/ignored
    period_start DATE,                       -- 诊断周期
    period_end DATE,
    created_at DATETIME
);
```

### 6.2 改进建议表

```sql
CREATE TABLE improvement_suggestions (
    id INTEGER PRIMARY KEY,
    suggestion_id VARCHAR(50) UNIQUE,
    diagnosis_id VARCHAR(50),                -- 关联诊断
    action_type VARCHAR(30),                 -- add_rule/adjust_threshold/...
    suggestion TEXT,
    action_params TEXT,                      -- JSON落地参数
    expected_impact TEXT,
    status VARCHAR(20) DEFAULT 'pending',    -- pending/approved/rejected/applied
    reviewed_by INTEGER,                     -- 审核人
    reviewed_at DATETIME,
    review_feedback TEXT,                    -- 驳回理由
    applied_at DATETIME,
    effect_measured_at DATETIME,             -- 回测时间
    effect_before FLOAT,                     -- 回测前指标
    effect_after FLOAT,                      -- 回测后指标
    created_at DATETIME,
    FOREIGN KEY (diagnosis_id) REFERENCES diagnosis_results(diagnosis_id)
);
```

**采纳接口的落地逻辑**（按 action_type 分发）：
```python
async def approve_suggestion(suggestion_id, user):
    s = get_suggestion(suggestion_id)
    if s.action_type == "adjust_threshold":
        apply_threshold_change(s.action_params)      # 自动生效
    elif s.action_type == "add_rule":
        add_scoring_rule(s.action_params)            # 写入规则表，下次评分生效

    s.applied_at = now()
    # 记录回测基线
    s.effect_before = get_current_metric(s.module_name)
```

## 九、闭环机制：建议→落地→回测

```
[诊断生成建议]
      ↓
[看板展示] → 管理员审核
      ↓
   ┌──采纳──┐    ┌──驳回──┐
   ↓        ↓    ↓
[落地]   [记录feedback]
   ↓
[30天后回测]
   effect_before vs effect_after
   ↓
[回测结果反馈到看板]
   "该建议有效/无效"
   ↓
[无效的建议模式 → 优化LLM prompt]
```

**回测逻辑**（确定性）：
```python
def measure_effect(suggestion):
    before = suggestion.effect_before        # 采纳时的指标
    after = get_current_metric(suggestion.module_name)
    suggestion.effect_after = after
    suggestion.effect_measured_at = now()
    # 判定有效性
    if suggestion.action_type == "add_rule":
        # 期望一致性率提升
        effective = after.consistency_rate > before.consistency_rate
    return effective
```

## 十、模型 vs 确定性边界（关键约束）

| 决策 | 执行者 | 理由 |
|------|--------|------|
| 检测异常 | **确定性阈值** | 指标是数字，阈值判断无需LLM（CLAUDE.md #7） |
| 聚类热点 | **SQL聚合** | 数据聚合是确定性操作 |
| 偏差模式分类 | **确定性规则** | bias_direction/confidence是数字判断 |
| action_type选择 | **确定性映射** | 模式→动作的映射表 |
| 根因解释 | **LLM** | 理解语义，模型擅长 |
| 建议内容生成 | **LLM+模板** | LLM生成，模板约束格式 |
| 是否落地 | **人工确认** | 改评分规则是高风险，必须人在环 |
| 效果回测 | **确定性计算** | 前后指标对比，纯计算 |

**铁律**：LLM从不直接修改系统——只建议，落地永远需人工点"采纳"。

## 十一、分阶段实施计划

### P1：确定性归因（2周，零风险）✅ 推荐先做
**目标**：看板能显示"问题+证据"，不含LLM
- 新增 `diagnosis_results` 表
- 实现 `DIAGNOSIS_RULES` 检测引擎
- 实现统计聚类归因（4.2 Step1）
- 看板新增"诊断"区，显示问题+热点+证据
- 定时任务：每日凌晨跑诊断

**交付物**：看板能显示"设施维护·屋面防水漏检（15次中12次被改，AI高估）"
**风险**：极低（纯只读分析，不改评分逻辑）

### P2：LLM建议生成（2周，低风险）
**目标**：诊断卡片显示完整"问题→根因→建议"
- 接入 DeepSeek 生成根因和建议
- 实现 `improvement_suggestions` 表
- 建议生成 Prompt 模板 + 结构化校验
- 看板卡片展示根因+建议+预期效果

**风险**：低（建议只读，不落地）

### P3：采纳闭环（3周，中风险）
**目标**：建议能一键落地并回测
- 实现 approve/reject API
- action_type 落地分发（add_rule/adjust_threshold 自动；refine_prompt 进审核队列）
- 30天回测任务
- 回测结果展示

**风险**：中（改评分规则/阈值，需充分测试，建议先开放 adjust_threshold（低风险）和 add_rule，refine_prompt 最后开放）

### P4：Prompt改进闭环（后续，高风险）
- refine_prompt 建议落地（需双人审核）
- prompt 变更灰度发布（先对1个项目生效，验证无回退再全量）

## 十二、风险与应对

| 风险 | 应对 |
|------|------|
| LLM建议不合理/有幻觉 | 建议必须附"证据"（具体scoring_id），管理员可核查；驳回feedback用于优化prompt |
| 采纳后评分质量下降 | 回测机制兜底；高风险动作（refine_prompt）进审核队列+灰度 |
| 诊断过度打扰 | severity分级，只在高严重度时强提醒；可配置诊断频率 |
| 数据不足导致归因不准 | 设最低样本量（如编辑次数<5不诊断），标注"样本不足，仅供参考" |
| LLM成本 | 根因/建议生成只在"有异常"时触发（非全量），且缓存诊断结果（每日1次） |

## 十三、验证方法

### P1 验证
